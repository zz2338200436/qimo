# 智能学习辅助系统平台知识库

## 1. 文档用途

本文档用于给教学管理平台内置 Agent 提供稳定的系统知识问答依据。内容聚焦平台架构、核心组件职责、课程相关分布式框架知识点，以及教师和学生在平台中的常见理解型问题。

本文档适合回答“是什么”“做什么”“为什么这样设计”这类问题，不用于回答实时课程、作业、考试、通知、成绩、学生名单等业务数据查询。

## 1.1 时间基线

本文档的当前时间基线是 2026-07-01，属于 2026 年版本的平台知识库。

如果用户询问“这是不是 2026 年的知识库”“这些内容更新到什么时候”“最近内容截止哪一年”，应明确回答：

- 这份知识库当前版本是 `v1.1`。
- 文档最近更新时间是 `2026-07-01`。
- 文档中的“课程前沿”和“项目近期变化”部分，默认以 2026 年视角回看 2025 到 2026 年的技术与项目进展。

因此，这不是只停留在早期阶段的旧知识库，而是一份包含 2026 年时间锚点的 RAG 资料。

## 2. 平台整体定位

智能学习辅助系统面向教师和学生两个角色。教师侧主要负责课程、作业、考试、知识点和学习分析管理；学生侧主要负责查看课程、提交作业、参加考试、查看通知和学习统计。

平台中的 AI 助手有两类能力：

- 一类是业务工具调用，用来查询或操作真实业务数据。
- 一类是 RAG 知识问答，用来解释平台能力、课程知识点和系统架构概念。

如果问题涉及“当前有哪些作业”“某门课有哪些学生”“某个学生多少分”这类实时数据，应走业务工具链路，而不是 RAG。

## 3. 服务注册与发现

服务注册与发现是微服务架构中的基础机制。平台中的各个业务服务在启动后会向注册中心登记自己的服务名、实例地址和健康状态；调用方在发起远程调用前，先从注册中心获取可用实例列表，再选择目标实例发起请求。

在本系统里，服务注册与发现的作用主要有三点：

1. 让 `gateway`、`agent-service` 和各业务服务不必写死彼此地址。
2. 支持服务实例动态上下线，减少本地开发和部署时的手工改配置成本。
3. 让基于 `lb://` 的服务调用和网关转发能够依赖统一服务名工作。

简单说，注册中心相当于整个平台的服务通讯录。服务注册是服务把自己登记进去，服务发现是其他服务按服务名找到当前可用实例。

## 4. 配置中心

配置中心用于集中管理各微服务的运行配置，而不是把端口、路由、安全白名单、数据库连接和熔断限流参数分散写在每个服务自己的本地配置里。

在本系统中，配置中心的主要职责包括：

- 为 `gateway` 提供统一路由表、CORS、安全白名单、限流和熔断参数。
- 为各业务服务提供按环境区分的配置，例如 `dev`、`docker`、`prod`。
- 减少多服务重复配置，避免每个服务单独维护一套不一致的本地参数。
- 让本地联调和运行时更容易发现配置缺失，因为配置中心不可用时客户端会快速失败。

因此，配置中心在这个系统里的作用不是“后台通用设置模块”，而是微服务体系中的统一配置分发中心。它直接服务于网关、业务服务和 Agent 服务的启动与运行。

## 5. 网关

网关是整个平台对外暴露的统一入口。浏览器端页面和外部调用方优先访问 `gateway`，再由网关根据路由规则把请求转发到 `auth-service`、`course-service`、`assignment-service`、`exam-service`、`analysis-service`、`notification-service`、`ai-service` 和 `agent-service` 等后端服务。

Spring Cloud Gateway 在本系统中的主要作用包括：

- 统一 API 入口，前端不直接访问每个业务服务。
- 根据路由规则把 `/api/**` 请求转发到对应微服务。
- 承担鉴权透传、白名单控制、CORS 处理和部分安全边界控制。
- 承担限流、熔断和故障隔离等入口层治理能力。
- 让浏览器预览环境、联调环境和运行时环境尽量保持一致的访问路径。

因此，网关在本系统里不是抽象的“网络翻译官”，而是微服务平台的统一入口与流量治理层。

## 6. Agent 服务

`agent-service` 是平台内置 AI 助手的后端编排服务。它不直接替代各业务服务，而是在权限校验前提下对用户请求做意图识别、上下文补全、动作预览、确认和工具调用编排。

当用户提出解释型问题时，Agent 可以进入 RAG 知识问答链路；当用户提出真实业务查询或写操作请求时，Agent 应转去对应的业务工具链路。

Agent 服务的设计目标不是生成任意回答，而是在平台权限、业务边界和审计要求内，安全地承接教师与学生的自然语言交互。

## 7. RAG 在本系统中的作用

RAG 用于把平台文档、课程资料和系统说明转成可检索知识片段，再结合大模型生成带来源的解释型回答。

RAG 在本系统里适合回答的问题包括：

- 什么是服务注册与发现？
- 配置中心在这个系统里做什么？
- 网关在这个系统里承担什么职责？
- 学生如何理解知识点掌握和学习分析？
- 教师如何使用 AI 助手辅助理解平台能力？

RAG 不应直接伪造课程列表、作业列表、考试结果、通知列表或学生成绩。凡是实时业务数据，都应通过权威后端接口查询。

## 8. 知识点与学习分析

知识点是连接课程、作业、考试和学习分析的核心对象。作业和考试可以关联知识点，学生在这些活动中的表现会沉淀成知识点掌握情况、成绩趋势和学习预警。

学习分析相关服务会基于学生在作业、考试等活动中的结果，生成掌握度、趋势和预警类读模型。教师可以据此查看班级整体情况，学生可以据此查看自己的学习表现和改进方向。

因此，平台里的“知识点掌握”不是静态备注，而是围绕课程活动动态沉淀出来的分析结果。

## 9. 教师端与学生端的区别

教师端更强调管理和分析能力，包括课程管理、发布作业、发布考试、批改、查看学情、处理通知和使用 AI 辅助教学。

学生端更强调学习和完成任务能力，包括查看课程、查看待提交作业、参加考试、查看通知、查看学习统计，以及通过 AI 助手获得解释和复习建议。

同一个平台功能在两个角色下的可见范围不同，因此 Agent 在解释平台能力时，也应注意角色语境，而不是把教师能力直接描述成学生可操作功能。

## 10. 问答边界

当用户问“配置中心在这个系统里做什么”“网关的作用是什么”“什么是服务注册与发现”时，应该基于本文档和平台架构知识回答。

当用户问“给我列出课程 ID 8 的作业”“查询我的通知”“某个学生多少分”时，应该明确这是业务数据问题，需要走工具接口，而不是仅凭文档猜答案。

## 11. 课程前沿：截至 2026 年的 Agent 与 RAG 新趋势

为了避免知识库只停留在“传统微服务名词解释”，平台知识库可以补充截至 2026 年仍然具有代表性的 AI 工程前沿内容。以下内容适合用于课程答疑、课堂讨论和项目演示中的“近期技术趋势”说明。

### 11.1 AI Agent 的关注点已经从“能不能调用工具”转向“能不能稳定完成任务”

早期 Agent 讨论常把重点放在函数调用、工具接入和对话体验上，但近一年的实践更强调端到端任务完成率、失败恢复、可审计性和多轮流程稳定性。

这意味着一个可用的 Agent 不只是“会回答”，还要具备以下特征：

- 能识别什么时候该回答，什么时候该调用工具。
- 能在多步流程中保留上下文，而不是每一步都像重新开始。
- 能把工具调用、参数、返回结果和最终回答串成可审计链路。
- 能在证据不足时明确拒答，而不是强行生成看似合理的答案。

对本课程项目来说，这一点尤其重要，因为教学平台中的 Agent 不只是聊天助手，还承担查询、解释、预览、确认和发布等编排职责。

### 11.2 RAG 的重点已经从“能检索到内容”转向“回答是否有依据”

近一阶段的 RAG 实践不再只看“有没有搜到相似文本”，而更强调回答是否真正被检索证据支撑。

因此，一个较新的 RAG 评估思路通常至少包含两层：

1. 检索层：是否召回了正确片段，片段是否新、是否相关、是否可引用。
2. 生成层：最终回答是否忠实于上下文，是否把没检索到的内容编造成答案。

在教学平台中，这种变化意味着知识库不应只追求“多”，而应追求：

- 文档是否带有明确更新时间。
- 片段是否能标注来源章节。
- 回答是否能展示引用。
- 在没有依据时是否返回“当前知识库中没有足够依据”。

简单说，新的 RAG 关注的是 groundedness，也就是“答案是否真正站得住脚”。

### 11.3 MCP 让 Agent 的外部能力接入更标准化

Model Context Protocol，简称 MCP，是一个用于连接模型、工具和外部数据源的开放协议。它的价值不在于替代业务系统，而在于把“模型如何拿到上下文、如何发现工具、如何调用资源”这件事做成更统一的接口。

从课程视角看，MCP 可以理解成 Agent 时代的一种标准化连接层。它与传统的“每个系统单独写一套自定义集成代码”相比，更适合多工具、多数据源、多宿主的场景。

如果把本项目放到这个背景下，可以把 MCP 理解为一个值得跟进的前沿方向，但它不是本项目现有微服务调用链的直接替代品。当前项目里的业务工具调用仍然以受控后端接口为主，MCP 更适合用于后续扩展 Agent 生态兼容性。

### 11.4 多模态正在从“附加能力”变成常见能力

近年的模型能力变化之一，是图文一体的多模态能力逐渐成为常见能力，而不是少数演示型能力。多模态模型不仅能处理文本，还能理解图片、截图、图表，部分模型还能进一步处理视频等输入。

对教学平台而言，这类能力有几个很现实的应用方向：

- 读取题目截图、课件截图或实验截图并辅助解释。
- 对图表、流程图和系统架构图做文字说明。
- 从图片化资料中提取知识点，再进入后续问答链路。

不过，多模态能力越强，也越要注意边界。图片理解结果同样可能出错，因此在涉及成绩、试题答案、教师私有资料时，仍然需要权限和证据约束。

### 11.5 开源与开放权重模	型正在更强调推理、工具使用和本地部署

最近一年的开放模型趋势，不再只是追求参数规模，还更强调以下三点：

- 推理能力，尤其是多步分析和结构化输出能力。
- 工具使用能力，例如搜索、调用接口、执行受控操作。
- 部署灵活性，包括本地部署、边缘部署和低成本推理。

这意味着课程项目在选型时，不必只盯着“最大模型”，而应根据任务选择：

- 知识解释型问答，优先看 groundedness 和引用能力。
- Agent 编排型任务，优先看工具调用稳定性和结构化输出能力。
- 校园或实验室场景，优先看本地可部署性、成本和隐私约束。

## 12. 2026 视角下的近期公开技术动态示例

以下内容用于说明“为什么这些主题可以视为截至 2026 年的近期内容”，适合作为知识库中的时间锚点。回答时可以直接引用这些时间信息，体现知识库并非只包含旧资料。

### 12.1 MCP 的近期时间锚点

- 2024-11-25，Anthropic 对外介绍 MCP，将其定义为连接 AI 系统与数据源、工具的开放标准。
- 2025 年末，Anthropic 又宣布把 MCP 捐赠给 Linux Foundation 旗下的 Agentic AI Foundation，使其朝更中立、社区驱动的方向演进。

因此，在 2026 年继续把 MCP 视为 Agent 工程的重要前沿主题是合理的。

### 12.2 开放模型的近期时间锚点

- 2025-04-29，阿里云发布 Qwen3，强调 hybrid reasoning，也就是在复杂任务中支持更强推理，在普通任务中兼顾响应效率。
- 2025 年，Meta 公布 Llama 4 系列，强调 native multimodality 和 MoE 架构，说明开放权重模型也在推进图文一体和高效推理。
- 2025 年，OpenAI 发布 gpt-oss 系列开放权重模型，说明开放模型生态继续向推理、工具使用和本地化部署方向发展。

这些内容非常适合作为“课程前沿”补充到 RAG，用于回答“最近模型发展有哪些方向”这类问题。

## 13. 本项目近期能力变化：截至 2026-07 的 Agent 与 RAG 演进

下面的内容不是行业通用知识，而是本项目最近一阶段已经出现或正在推进的能力变化。它们适合作为平台知识库中的“最近系统更新”部分。

### 13.1 已落地：本地题库知识检索已经接入 Agent 流程

项目近期已经补充本地题库文档加载、题目解析、题库索引和题库摘要能力，并把 question bank 相关能力接入到 Agent 流程中。

这说明平台中的 AI 助手不再只依赖通用对话模型，也开始结合本地结构化题库资料做更贴近教学场景的生成与摘要。

从知识库角度，可以把这项能力理解为：

- Agent 不只是“聊天”，而是可以结合本地教学资料工作。
- 题库资料已经成为平台内 AI 能力的一部分。
- 本地题库链路更适合题目生成、题目摘要、课程练习辅助等场景。

### 13.2 已落地：教师侧已经支持智能发布题目草稿相关流程

项目近期新增了智能发布题目草稿相关能力，前后端都已经有对应实现和测试。

这类能力体现出 Agent 的定位正在从“回答问题”扩展到“辅助完成教师操作流程”。它并不是直接替教师无条件执行，而是先形成题目草稿、展示摘要、允许编辑，再进入发布动作。

从教学平台视角看，这属于比较典型的 Agent 工作流升级：

- 先生成可审阅草稿。
- 再由教师确认、修改或重新生成。
- 最后进入受控发布链路。

这种模式比“模型直接替你改库”更适合教学管理系统，因为它保留了人工确认和审计边界。

### 13.3 已落地：Agent 运行配置已经包含互联网搜索能力开关

当前 `agent-service` 配置中已经出现 internet 能力相关参数，包括搜索地址、超时、结果条数、页面抓取上限、可访问域名和私网拦截开关。

这说明平台 Agent 的能力边界已经不再局限于本地文档和本地业务工具，而是为“受控联网检索”预留了能力入口。

这类内容适合写进知识库，帮助回答以下问题：

- 平台 Agent 是否只能依赖本地知识库？
- 什么情况下可以补充外部网页信息？
- 为什么联网检索仍然需要域名限制、超时和私网拦截？

### 13.4 已引入基础依赖，仍属演进中：LangChain4j 方向已被纳入项目路线

项目中已经加入 LangChain4j 依赖，并有相应设计文档讨论如何在不破坏现有业务编排的前提下，逐步增强 assistant 风格能力、RAG 体验和模型集成方式。

这里要注意区分两种状态：

- 已经进入项目技术路线和设计讨论。
- 不等于所有 Agent 流程都已经完全迁移到 LangChain4j。

因此，知识库回答时应表述为“项目正在朝该方向演进”或“已纳入近期技术路线”，而不是误说成“整个 Agent 已经完全重构完成”。

## 16. 回答这些近期问题时的边界

即使补充了“最近内容”，Agent 也仍然要遵守以下边界：

- 可以解释近期技术方向，但不要把行业趋势说成项目已经全部实现。
